JVM-aware in-place Pod right-sizing for Kubernetes, with zero restarts

Warden makes a running JVM give memory back to the OS during predictable quiet windows, then lowers the Pod’s request and limit in place. The pod stays up, its warm state stays intact, and your replica count never changes.

Status and compatibility
  • Beta. Controller, agent, CRDs and both Helm charts are released and work end to end on a real cluster; not battle-tested under production load, APIs (v1alpha1) may change. Boost is experimental.
  • Kubernetes 1.35+ (in-place Pod resize is GA), or earlier with the InPlacePodVerticalScaling feature gate. Nodes must use cgroup v2.
  • ZGC / Shenandoah: a settable soft heap ceiling at runtime. G1: periodic GC, no live soft-max, so launch with an -Xmx that already covers your largest target. Serial/Parallel/Epsilon: read-only.
  • A Cluster Autoscaler (or equivalent) is what turns lower requests into a smaller bill.

The safety handshake, step by step

Shrink and grow are not symmetric. Pick a scenario and step through it, or click a message.

  • Shrinking: shrink the JVM first, verify RSS actually fell, then lower the cgroup.
  • Growing: raise the cgroup first, then the JVM’s soft max.
  • Aborting is a normal outcome: if RSS will not drop, the soft max is restored and the cgroup is never touched. See the state machine.

Install in three steps

helm repo add warden https://baokhang83.github.io/mnemo-jvm-warden/
helm repo update
helm install warden warden/warden

Then include the warden-sidecar library chart in your app’s chart and add a WardenPolicy. Neither chart makes Warden act on its own; it acts only once a policy targets the workload.

apiVersion: warden.mnemo.io/v1alpha1
kind: WardenPolicy
metadata:
  name: my-app-policy
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: my-app }
  timezone: Europe/Paris
  profiles:
    off-peak: { request: 512Mi, limit: 768Mi }
    peak: { request: 2Gi, limit: 3Gi }
  schedule:
    - { cron: "0 22 * * *", profile: off-peak }
    - { cron: "0 7 * * *", profile: peak }

FAQ

Why does Kubernetes in-place Pod resize OOMKill Java applications?

Two different causes. First, the memory limit was lowered while the JVM still held more committed heap than the new limit: the kernel kills the process when it touches memory that no longer fits. The kubelet tries to hold a limit decrease back while usage is above it, but Kubernetes documents that check as best-effort, and a JVM's committed heap counts as used even when mostly free. Second, the new limit is below what -Xmx plus non-heap memory needs: -Xmx cannot change on a running JVM, so the pod survives the shrink and is killed later when the working set grows. Warden fixes the first by making the JVM release memory and verifying RSS before it lowers the cgroup; you fix the second by sizing the smallest profile limit above -Xmx plus non-heap overhead.

Does mnemo-jvm-warden work with G1GC or only ZGC and Shenandoah?

It works with G1, ZGC and Shenandoah for scheduled right-sizing. ZGC and Shenandoah expose a settable soft heap ceiling (SoftMaxHeapSize) at runtime. G1 has no live soft-max, so Warden forces a GC and relies on G1 periodic GC to uncommit, which is safe but slower, and a G1 workload must launch with -Xmx already covering its largest target. Serial, Parallel and Epsilon cannot uncommit freed pages, so the agent stays read-only for them.

How does Warden prevent a sidecar from escalating privileges across Pods?

The sidecar's Role grants pods/resize patch and pods get only on its own pod name (resourceNames). Deployments and StatefulSets have generated replica names, so they need a namespace-wide grant; a ValidatingAdmissionPolicy then requires the caller's bound service-account token pod-name claim to match the pod being resized, and replica A resizing replica B is denied. That policy is not installed by the Helm chart: apply it yourself for any Deployment or StatefulSet target. Neither the controller nor the agent is granted any verb on secrets.

Do I still need a Cluster Autoscaler?

Yes, or an equivalent that consolidates nodes. Warden lowers the Pod's resource request, which frees schedulable capacity, but it never changes the number of pods or nodes. Without node consolidation the freed capacity is not billed capacity.

Why not just set resizePolicy to RestartContainer?

RestartContainer is safe for a JVM and needs no extra tooling, but it restarts the JVM: compiled code, loaded classes, pools and in-process caches are lost. Warden is for slow-starting applications, minimum-replica setups and stateful or cache-heavy workloads where that is not acceptable.
