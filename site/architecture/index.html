Architecture: the safe resize handshake and its internals

Components, the asymmetric shrink and grow sequences, the RSS verification gate, how Warden reads the cgroup and controls the JVM, and the invariants that keep a resize from OOMKilling a pod.

Components

ComponentScopeWhat it does
warden-controllerCluster-wide, one replicaReconciles WardenPolicy and WardenBoost: resolves the schedule, lead time, blackout and guardrail precedence, and writes the target request/limit as annotations on the pods it owns. It never resizes a pod itself.
warden-agentNative sidecar, one per JVM podThe safety-critical part. Polls its own pod’s intent, drives the JVM, verifies RSS, issues the in-place resize and confirms the kubelet applied it. Needs shareProcessNamespace: true, JMX on loopback and a read-only host cgroup mount.

The sidecar is deliberately simple about policy and strict about safety: the controller says what and when; the agent decides whether it is safe now.

The state machine

Every transition is a state machine in the agent, not a linear script, because a shrink can legitimately abort if the JVM will not give memory back, for example when real load arrives mid-shrink.

Shrink path

  1. Shrinking: lower SoftMaxHeapSize and ask the cache hook to flush evictable entries. No cgroup change yet.
  2. Draining: force a deep GC and uncommit; pages return to the OS.
  3. Verifying (the gate): read actual RSS. Only if it is below the new limit, with a safety margin, does the agent proceed.
  4. Resizing: PATCH pods/resize, lowering request and limit together. The request is what frees capacity for the autoscaler.
  5. Aborted: if RSS will not drop, restore the soft max and leave the cgroup untouched. A rejected shrink is a no-op, not a degraded state.

Grow path, asymmetric on purpose

  1. Expanding: raise the cgroup (request and limit) first. Headroom must exist before the JVM reaches for it.
  2. Warming: raise SoftMaxHeapSize, then optionally pre-warm the cache ahead of the predicted traffic.

Emergency path: a guardrail metric above emergencyGrowAbove in the low state skips the schedule and goes straight to Expanding. The pod is already warm, so recovery is a resize, not a cold start.

RSS verification and cgroup monitoring

  • The agent reads resident memory from the cgroup v2 memory.current file through a read-only hostPath mount of /sys/fs/cgroup at /host-cgroup, plus JVM GC/NMT telemetry. cgroup v1 is out of scope.
  • Some collectors uncommit asynchronously, so the gate waits for pages to actually return, not just for the GC to finish. On timeout (WARDEN_GC_TIMEOUT_SECONDS, default 30) it aborts.
  • If the cgroup cannot be found, the agent says which of two things is wrong: the mount is missing, or the node is on cgroup v1.

JMX and JVM controls

The agent drives the runtime knobs through the Attach API / JMX (HotSpotDiagnosticMXBean-style controls such as SoftMaxHeapSize, GC.run, native memory tracking). It never touches -Xmx. The target must expose JMX on 127.0.0.1 only: the loopback binding is what makes unauthenticated JMX acceptable. See the threat model.

Intent handoff and timing

  • The controller writes two byte-count annotations, warden.mnemo.io/target-request-bytes and target-limit-bytes, on the target pods. The agent reads only its own pod.
  • Precedence per reconcile: blackout > metric > schedule.
  • The controller resyncs at least every 30 s; the agent polls every 5 s by default. A transition can therefore lag its cron edge by up to ~35 s: budget for it in spec.leadTime.

What can still go wrong

  • Uncommit lag: the gate must wait for pages, not for GC completion; timeout means abort.
  • No node consolidation: lower requests free schedulable capacity but not billed capacity.
  • cgroup v1 nodes: unsupported.

Boost path (experimental)

A WardenBoost asks for a named, operator-approved memory floor for one Pod and container. The controller validates admission, claims the Pod, and grants only after matching agent evidence. The policy reconciler remains the single intent writer: it combines the floor with scheduled and emergency targets, respects blackout and shrink guards, and the agent applies the normal grow/shrink ordering. Scheduled-only operation is unchanged without any Boost. See the Boost guide.
