Boost API: let a Java application request temporary memory in Kubernetes

A scheduled right-sizing curve cannot know about a bounded, named operation: an index rebuild, a nightly batch, a migration. Boost lets the application take a memory lease for exactly that, and give it back when done, with no kubectl and no Kubernetes credentials in the app.

Experimental. Treat Boost as a controlled evaluation for a trusted operator in a controlled cluster, not as a production multi-tenant interface. Scheduled right-sizing works exactly the same without ever creating a Boost request.

1. The operator approves what can be asked for

A named Boost is defined in the WardenPolicy; the application cannot supply its own quantities.

spec:
  profiles:
    maintenance: { request: 1Gi, limit: 2Gi }
  boosts:
    index-rebuild:
      profile: maintenance
      heapTarget: 1Gi
      acquisitionTimeout: 2m
      maxDuration: 20m

2. The application takes a lease

warden-boost-client (Java 21, no third-party dependencies) is on Maven Central:

<dependency>
  <groupId>io.github.baokhang83.mnemo</groupId>
  <artifactId>warden-boost-client</artifactId>
  <version>0.2.1</version>
</dependency>
WardenBoostClient warden = WardenBoostClient.discover();

try (BoostLease lease = warden.acquireBoost("index-rebuild", Duration.ofMinutes(2))) {
    // Reached only after a durable Granted, never for a merely pending request.
    rebuildIndex();
    // close() requests completion; it is idempotent and does not block on reclamation.
} catch (BoostRejectedException e) {
    // Definite: this request will not be granted. No lease was handed out.
    log.warn("boost rejected: phase={} {}", e.phase(), e.getMessage());
} catch (BoostAcquisitionTimeoutException e) {
    // Uncertain, not failed: the grant may still be racing server-side.
    reconcileLater(e.requestId());
}

discover() reads WARDEN_BOOST_PORT and WARDEN_BOOST_TOKEN_PATH from the environment, matching the agent’s defaults, so an app container usually needs no extra configuration, only the shared token volume mount.

BoostRejectedException vs BoostAcquisitionTimeoutException

They are separate types on purpose. A caller cannot treat “definitely rejected” as “might still be granted”, because an uncertain grant that gets released can mean an operation already running without its memory floor.

MeaningThe client observed a terminal, non-granted phase. This call returned no lease.This call gave up waiting before the request settled. Outcome uncertain.

The client checks its timeout between HTTP calls, so a call already in flight can make the elapsed time exceed it. lease.status() re-fetches the current phase. Close the lease only after the boosted operation and its child work finish; there is no async or cancellation wrapper yet.

How it stays safe

  • Loopback only. The client talks to a local API on 127.0.0.1 served by the Warden sidecar (default port 8090). The app never holds Kubernetes credentials.
  • Pod-bound bearer token. The agent generates a fresh random token at every start and writes it (0600) to an emptyDir shared with the app. Loopback alone does not separate containers in one pod, so every call needs Authorization: Bearer <token>, compared in constant time. Run the app and sidecar as the same UID, or use another verified credential-sharing arrangement. Read the token fresh per call (or on a 401), because a sidecar restart regenerates it.
  • Admission binding. A ValidatingAdmissionPolicy (boost-request-guard) binds every self-requested boost to the requesting Pod’s own identity. Agent RBAC on wardenboosts is get/list/watch/create/patch, never delete and never the status subresource.
  • Prepared before granted. Warden prepares the allocation and the JVM before it records a grant, then returns the Pod to its current policy target once the lease closes. Expiry does not stop your Java code and does not release the floor.

Enable it

On the warden sidecar container, WARDEN_BOOST_POLICY_REF (the policy name to stamp on requests; its presence is the feature flag) and WARDEN_POD_UID (Downward API metadata.uid). Mount the token volume read-write in the sidecar and read-only in the app, and install the chart with the opt-in security package:

helm upgrade warden warden/warden --set boost.security.enabled=true

The security package is scoped to namespaces carrying the warden.mnemo.io/boost-enabled: "true" label, and role bindings are operator-managed. Without it, acquire calls reach the Kubernetes API and are denied by RBAC. Existing installations must apply updated CRDs before helm upgrade, because Helm does not upgrade installed CRDs.

Local API endpoints

POST /v1/boost/acquireBody {"boost":"<name>","requestId":"<optional>"}. Blocks up to WARDEN_BOOST_ACQUIRE_WAIT_SECONDS (25), then returns 202 so the caller polls. Reusing a requestId never creates a second WardenBoost. One outstanding request per agent: a second one gets 409.
GET /v1/boost/status?requestId=Current phase; 404 if unknown.
