Threat model: trust boundaries, RBAC and hardening for Warden

Warden mounts the host cgroup filesystem, attaches to a JVM over JMX and patches Pod resources. This page summarises what it can touch, who could abuse that, what already stops them, and which gaps are accepted rather than hidden. It is a summary: the full document is linked at the end.

How to read “verified”. A claim marked verified is proven by a unit test or a deploy/verify-*.sh script against a real kind cluster, not just by the YAML looking right. Warden is beta and pre-1.0; the project has no external security audit.

Trust boundaries

BoundaryWhat crosses itHow it is controlled
Namespace → cluster scopeThe controller’s ClusterRole reads wardenpolicies and gets/lists/patches pods cluster-wide.The code path only acts inside the policy’s own namespace (derived from the policy object; no CRD field can name another). Enforced in application code, not RBAC, so it needs a regression test.
Pod → nodeA read-only hostPath mount of /sys/fs/cgroup gives read visibility into every cgroup on the node.Read-only; Kubernetes has no native way to scope it to one pod’s subtree. An explicit, accepted cost. PodSecurity restricted/baseline forbid it, so an exemption is needed.
app container → sidecarshareProcessNamespace: true exposes the process table; JMX and the Boost API share the pod’s network namespace.Sidecar runs non-root; JMX bound to 127.0.0.1; Boost API needs a bearer token on a shared emptyDir. Run app non-root.
Replica → replicaSame ServiceAccount, different pod: a Deployment sidecar could try to resize its sibling.Closed by the warden-resize-admission-policy ValidatingAdmissionPolicy (verified: replica A resizing replica B is denied with HTTP 422).

RBAC least privilege

Every verb is mapped to the code path that needs it; a grant without a caller is a bug. deploy/verify-rbac-boundaries.sh asserts, with kubectl auth can-i --as=, that these grants hold and that a set of others is denied.

A real, documented tradeoff.

ValidatingAdmissionPolicy and token binding

  • Resize policy. It requires the caller’s bound service-account token’s authentication.kubernetes.io/pod-name claim to equal the pod being resized. It is not installed by the Helm chart; apply it for any Deployment or StatefulSet target.
  • Boost policies (opt-in, boost.security.enabled=true, selected namespaces only) bind every self-requested WardenBoost to the agent token’s Pod UID and name, restrict Pod metadata edits to the acknowledgement, limit resize to that Pod, protect status and request ownership metadata, and require automatic token mounting to be disabled with projected service-account tokens mounted only in the Warden init container.
  • Neither controller nor agent has any verb on secrets, and the agent’s bearer token and JMX responses are never logged. The agent re-reads its projected token on every call instead of caching it.

Operator hardening checklist

Required for the trust model to hold

  • Target JVMs use exactly the documented JMX flags, especially jmxremote.host=127.0.0.1. Test the binding from a second pod rather than trusting the launch command.
  • app containers run non-root wherever shareProcessNamespace: true is set.
  • The resize admission policy is applied for every Deployment/StatefulSet target.
  • A hostPath exemption exists if the cluster enforces PodSecurity restricted or baseline.

Recommended

  • A NetworkPolicy around the agent’s port 8080, and a secured path to Prometheus.
  • Restrict write access to wardenpolicies and who may target whose workloads.
  • Restrict pods/exec into the warden container: the image bundles harness entry points that can drive a resize with the sidecar’s token.
  • For Boost: restrict pods/exec, pods/ephemeralcontainers and serviceaccounts/token; a user able to create a Pod with the dedicated agent service account can impersonate the agent with another image.

Re-run deploy/verify-rbac-boundaries.sh after any RBAC change, and deploy/verify-cross-pod-resize-denied.sh for Deployment/StatefulSet targets, to confirm enforcement in your cluster.

Reporting a vulnerability: see SECURITY.md. Only the latest 0.x release is supported; fixes land on main and ship in the next release.
