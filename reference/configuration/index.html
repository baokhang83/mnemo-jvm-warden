WardenPolicy (warden.mnemo.io/v1alpha1)

apiVersion: warden.mnemo.io/v1alpha1
kind: WardenPolicy
metadata:
  name: warden-policy-sample
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: my-app }
  timezone: Europe/Paris
  profiles:
    off-peak: { request: 128Mi, limit: 256Mi }
    peak: { request: 384Mi, limit: 512Mi }
  schedule:
    - { cron: "0 22 * * *", profile: off-peak }
    - { cron: "0 7 * * *", profile: peak }
  leadTime: { shrink: 5m, warm: 10m }
  blackout:
    - { start: "2026-12-24T00:00:00Z", end: "2026-12-26T00:00:00Z" }
  guardrail:
    metric: 'sum(rate(http_requests_total[5m]))'
    shrinkBelow: "1"
    emergencyGrowAbove: "100"
FieldType / requiredNotes
spec.targetRefapiVersion, kind (Pod, Deployment, StatefulSet), nameSame shape as an HPA’s scaleTargetRef; the target is in the policy’s own namespace. For Deployments/StatefulSets the controller re-patches every owned pod each resync.
spec.timezoneIANA zone, requiredEvery cron window is evaluated in this zone, DST-correctly.
spec.profilesmap of name → request, limit, optional heapTarget; max 64Quantities as Kubernetes strings. heapTarget (positive integral bytes, below limit) only affects correlated Boost transitions.
spec.boostsoptional map; max 32Each names an approved profile with heapTarget, acquisitionTimeout, maxDuration. See the Boost guide.
spec.schedule[]cron (5-field), profileThe window whose cron most recently fired wins; order does not matter.
spec.leadTimeshrink, warm durationsFire at window_start − shrink and peak_start − warm, so the resize finishes before the traffic shift.
spec.blackout[]start, end ISO-8601Hard “do not touch”; UTC regardless of timezone. Beats every other signal.
spec.guardrailmetric (PromQL), shrinkBelow, emergencyGrowAboveNeeds the controller’s WARDEN_PROMETHEUS_URL. If the query fails or returns nothing, the metric is “unverified”: shrinkBelow vetoes the shrink (fails closed) and the emergency grow never fires.
statusread-onlycurrentProfile, currentMetricValue. A profile in status is not confirmation that the resize applied.

CRDs: WardenPolicy · WardenBoost (experimental, created by the Boost client or an operator for a named Boost) · sample policy.

Precedence and timing

  1. Blacked out: nothing changes.
  2. Metric above emergencyGrowAbove: grow immediately, skipping the schedule.
  3. Candidate is a shrink and the metric is not below shrinkBelow: the shrink is vetoed.
  4. Otherwise the schedule’s candidate, adjusted for lead time, applies.

The controller reconciles on every change and at least every 30 s; the agent polls every 5 s. Budget up to ~35 s of lag in leadTime.

The agent also needs a read-only hostPath mount of /sys/fs/cgroup at /host-cgroup, and shareProcessNamespace: true on the Pod.

Helm charts: warden vs warden-sidecar

ChartTypeWhat it installs
wardenapplication chartThe WardenPolicy and WardenBoost CRDs, controller RBAC and the controller Deployment (one replica, Recreate, no leader election yet). Also exposes the sidecar as an includable named template.
warden-sidecarlibrary chartRenders nothing itself, so depending on it can never deploy a second controller. Your app chart includes warden.sidecar (the native-sidecar init container) and warden.sidecar.volumes; your chart still sets shareProcessNamespace and the host-cgroup volume.
helm repo add warden https://baokhang83.github.io/mnemo-jvm-warden/
helm repo update
helm install warden warden/warden
controller:
  image: { repository: ghcr.io/baokhang83/mnemo-jvm-warden-controller, tag: latest }
  prometheusUrl: ""        # -> WARDEN_PROMETHEUS_URL
  resources:
    requests: { cpu: 100m, memory: 256Mi }
    limits: { cpu: 500m, memory: 512Mi }
sidecar:                   # reference defaults for the warden.sidecar template
  enabled: true
  image: { repository: ghcr.io/baokhang83/mnemo-jvm-warden, tag: latest }
  targetContainerName: app # -> WARDEN_TARGET_CONTAINER_NAME, no default
  healthPort: 8080
  gc: { timeoutSeconds: 30 }
  resize: { timeoutSeconds: 30 }
  intentPollIntervalSeconds: 5
boost:
  security: { enabled: false, namespaceSelector: { matchLabels: { warden.mnemo.io/boost-enabled: "true" } } }
  observability: { enabled: false, port: 8081 }

In your app chart: add the dependency warden-sidecar from https://baokhang83.github.io/mnemo-jvm-warden/ (match the published version, see helm search repo warden), a warden: values block with targetContainerName and resources (no defaults), and include the template under initContainers. A hand-authored equivalent is deploy/example-sidecar.yaml. Helm does not upgrade installed CRDs on helm upgrade: apply updated CRDs first. controller.resources defaults are deliberately not tight: a 256Mi limit OOMKilled the controller under load.

The Boost observability setting exposes an unauthenticated metrics Service and grants Events creation; protect it with a NetworkPolicy.

Runbook

Start at the agent: GET /healthz (liveness), /readyz (200 once attached to the JVM), /metrics (Prometheus: warden_resizes_total, warden_aborts_total, warden_bytes_reclaimed_total, warden_target_rss_working_set_bytes, warden_gc_supported).

SymptomWhat it means / what to check
/readyz stays 503The agent has not attached to the target JVM. Check WARDEN_TARGET_CONTAINER_NAME matches a sibling container; the agent retries with backoff for the first seconds.
“Agent is read-only for this target”; warden_gc_supported{collector="OTHER"} is 0The collector cannot uncommit (Serial, Parallel, Epsilon). Not a bug: switch the target to G1, Shenandoah or ZGC. There is no flag to force it.
warden_aborts_total climbing, no shrink recordedThe verification gate refused: the working set genuinely does not fit the profile yet. Compare warden_target_rss_working_set_bytes with the profile’s limit; raise the profile, check cache shedding, or increase leadTime.shrink. The cgroup was left untouched.
“could not find a cgroup directory … is the hostPath mount configured?”The sidecar lacks the read-only /sys/fs/cgroup mount (the chart wires it; hand-written manifests may not).
“not on cgroup v2 (no memory.current)”The node runs cgroup v1, which is unsupported.
Guardrail never evaluates; shrink vetoed foreverCheck, in order: WARDEN_PROMETHEUS_URL is set on the controller; the PromQL returns a series (empty equals failure, and fails closed); controller logs for “failed to evaluate guardrail metric”.
Blackout at the wrong timeBlackout timestamps are absolute and evaluated in UTC; convert local times to Z.
status.currentProfile updates but pod limits never changeCheck controller logs for “failed to emit intent”, the targetRef name/kind/namespace, and the agent’s /readyz.
